# v0.1.166 Release Conflict Resolution Design

## Goal

Integrate the verified upstream Stable Release `v0.1.166` into
`origin/custom-release`, preserve both the upstream panel API rate limiter and
the custom extension risk-event middleware, repair conflict-base diagnostics,
and publish the validated result through the existing two-phase production
release workflow.

- Current production Stable Release: `v0.1.165` at
  `e9a58c1cb8b5ef626a75c93b4d953fde5e67aa29`.
- Target annotated Stable Release: `v0.1.166`, peeled commit
  `dc893dd0b8eab41df5be595ae9fcd1aa74a062b8`.

  `backend/internal/server/router.go`.
- Production remains healthy and unchanged at Official `v0.1.165`, Custom
  `v1.0.7`.

## Selected Approach

Perform a minimal semantic merge in an isolated local worktree. The resolved
router will:

1. Construct the upstream `panelRateLimiter`.
2. Pass it to the Auth, User, Admin, and Payment route registrars.
3. Keep `RegisterCustomExtensionRoutes` and its returned custom gateway risk
   middleware.
4. Pass `customExtensions.GatewayRiskEvents` to the custom Gateway registrar.

This design deliberately avoids a broader Gateway extension refactor during a
Stable Release upgrade. Such a refactor could reduce one future conflict
surface but would broaden runtime risk and cannot eliminate conflicts when
upstream changes the same assembly boundary.

## Diagnostic Contract Repair

The conflict producer currently records the approved branch base as
`base_commit`, while the public API and frontend conflict panel read
`conflict_base`. The repair has two compatible parts:

- `deploy/ops/sync-upstream.sh` records `conflict_base` with the same approved
  branch commit while retaining `base_commit` for the general release job
  contract.
- `CustomReleaseBadge.vue` falls back to `base_commit` when reading an older
  conflict record that lacks `conflict_base`.

The result is backward compatible with the existing failed job and correct for
future conflict snapshots.

## Testing Strategy

The merge resolution preserves two already implemented behaviors. It will be
validated by compiling and running the upstream panel-rate-limit tests, the
custom server and route tests, and the wider backend suite required by the
repository. No synthetic source-text test will be added for the router merge.

The diagnostic repair follows a red-green cycle:

1. Add or extend a deployment contract test that fails because conflict
   metadata does not contain `conflict_base`.
2. Add or extend a frontend test that fails because a legacy status containing
   only `base_commit` renders `-`.
3. Implement the producer field and frontend fallback.
4. Run the focused deployment and frontend tests, then the repository release
   gates, backend tests, frontend typecheck/tests/build, and diff checks.

## Integration And Release Flow

1. Merge the verified `v0.1.166` tag into the isolated branch and resolve the
   single router conflict semantically.
2. Implement and test the diagnostic contract repair.
3. Review the complete merge diff and commit history, then integrate the
   validated branch into local `custom-release` without rewriting history.
4. Push only `origin/custom-release` using the local GitHub identity.
5. Wait for the `Custom Release` workflow for the exact pushed commit and
   verify both public GHCR images have that revision.
6. Trigger the administrator-equivalent durable update job on `US-RN-66`.
7. Wait for the job to prepare an immutable manifest and backup, then apply the
   same prepared job within its one-hour validity window.
8. Verify `release-state.json`, source commit, both immutable image digests,
   container health, internal health endpoints, and the public HTTPS site.

## Failure Handling

- Any additional merge conflict stops local integration for review.
- Any test or diff-check failure stops before push.
- Local GitHub authentication failure does not authorize VPS-based pushing.
- Failed Actions or missing/mismatched GHCR images stops before prepare.
- Prepare failure leaves production unchanged.
- Apply or health failure must use the existing automatic paired image rollback;
  neither database is restored automatically.
- No force-push, `git reset --hard`, blanket `ours`/`theirs` resolution, direct
  container edit, or direct publisher invocation is permitted.

## Success Criteria

- `origin/custom-release` contains the v0.1.166 merge and diagnostic repair.
- Relevant local and CI release gates pass for the exact pushed commit.
- Both GHCR images identify that same commit.
- The durable two-phase update finishes successfully.
- Production reports Official `v0.1.166`, retains the expected Custom version
  progression, and runs healthy paired application and extension images.
- A future conflict status displays the approved base commit instead of `-`.
