# 风控管理台产品与实现规格

状态：开发规格，作为风控管理台通用功能和验收的产品参考。

真实 IP、IP 地区、浏览器实例、关联账号、身份数据保留、Shadow 规则和风险摘要重算的完整设计，见
[`RISK-CONTROL-IDENTITY-ASSOCIATION-DESIGN.md`](RISK-CONTROL-IDENTITY-ASSOCIATION-DESIGN.md)。身份关联功能与本文冲突时，以该专项设计中已经确认的产品决策和安全边界为准。

## 1. 背景与当前事实

当前仓库已经包含独立 Go 风控服务、Sub2API 管理端代理以及三个管理页面：

- `frontend/src/views/admin/UserRiskControlUsersView.vue`：用户与风险事件
- `frontend/src/views/admin/UserRiskControlRulesView.vue`：场景规则配置
- `frontend/src/views/admin/UserRiskControlAuditView.vue`：操作记录

这三个页面保留，不再继续拆分成七个页面。当前实现可以读取用户、规则和审计数据，也支持单个用户封禁/解封和规则修改，但仍存在以下已确认缺口：

- 页面直接显示 `login_failure`、`critical`、`reject_candidate` 等内部枚举，普通管理员无法理解。
- 规则页只有修改已有规则，没有新建规则能力。
- 用户页没有批量选择、全选、批量封禁/解封。
- 用户表和审计表没有可用的表头排序。
- 过滤项和操作结果仍有英文原始值。
- 风险原因没有稳定的中文解释，也没有保证显示用户账号、事件时间和证据。
- 审计数据需要明确记录管理员账号、目标、原因、结果和失败信息。

本规格只描述实际需要落地的管理能力，不把机器学习、黑名单图谱或不可解释的综合模型作为本阶段前置条件。

## 2. 产品目标

管理员打开 Sub2API 左侧风控菜单后，应能在三个页面内完成：

1. 找到全部用户及其注册、登录、API、内容、配额和上游错误风险。
2. 看懂风险是什么、为什么命中、涉及哪个用户和哪些证据。
3. 对单个或多个用户执行封禁、解封，并留下可追溯原因。
4. 新建、编辑、启停和测试场景规则。
5. 查询所有风控和管理员操作记录，定位失败原因。

内部代码值可以继续作为 API 协议值，但不得直接作为主要界面文本展示。

## 3. 页面范围

### 3.1 用户与风险事件

页面名称建议为“用户风控”，菜单说明为“全部用户、风险事件与账号处置”。页面不是只显示高风险用户，而是支持查看全部已关联用户；风险字段为空时显示“暂无风险记录”。

#### 必须展示的用户信息

- 用户 ID
- 用户名、邮箱或账号标识
- 账号状态：正常、已封禁、待审核等
- 风险类型和中文名称
- 风险等级和风险分
- 风险原因
- 事件次数、IP 数、设备数
- 最近事件时间
- 最近一次处置动作和处理状态

风险原因必须优先显示可读文本，例如“命中规则：登录失败爆发（5 分钟内失败 5 次）”。如果后端暂时只有内部原因，应由前端根据规则名称、事件类型、计数和分数生成中文兜底说明；原始原因可以放在详情中的“原始数据”折叠区，不作为主表文本。

#### 筛选

所有选项显示中文，提交 API 时仍使用稳定的内部值：

| 界面选项 | API 值示例 |
|---|---|
| 账号状态 | `active`、`disabled`、`pending` |
| 风险类型 | `registration_attempt`、`login_failure`、`api_error`、`content_risk`、`quota_exceeded`、`upstream_error`、`api_request` |
| 风险等级 | `low`、`medium`、`high`、`critical` |
| 处理状态 | 待处理、已观察、已复核、已封禁、已解封 |

支持账号/邮箱/用户 ID 搜索、时间范围、风险分范围和“只看有风险记录”。点击“应用筛选”后回到第一页，并保留筛选条件。

#### 排序

以下表头必须可点击排序，显示当前升序/降序状态：风险分、风险等级、事件次数、最近事件时间、账号创建时间。排序参数应明确传给后端（例如 `sort_by`、`sort_order`），后端不支持时才允许在当前页做稳定排序；不能只做视觉上的箭头。

#### 批量处置

- 支持当前页全选、取消全选和单行选择。
- 选择用户后显示批量操作栏和已选数量。
- 支持批量封禁、批量解封、批量标记为已处理。
- 批量封禁/解封必须二次确认，并要求填写原因；原因不能为空且不能只包含空格。
- 操作逐项返回成功、失败和失败原因，不能因为一项失败就隐藏其他结果。
- 批量操作完成后刷新列表、清除已选项，并在操作记录中留下每个目标用户的记录。
- 管理员无权限或目标账号状态不允许操作时，明确显示“未执行”和后端原因。

批量接口可以先复用现有单用户状态接口逐项执行，但必须有并发上限、部分失败结果和审计记录；如果后端批量接口能保证事务边界，再升级为正式批量接口。

#### 详情抽屉

详情抽屉必须包含用户身份、当前账号状态、风险摘要、风险原因、风险分解释、事件时间线、涉及 IP/设备、最近处置记录和单用户封禁/解封入口。详情中的事件必须显示事件名称、发生时间、结果、错误原因和关联规则，不得只显示 JSON 字段名。

### 3.2 场景规则配置

页面名称为“场景规则”。V2 身份规则按邮箱、真实 IP、浏览器实例和综合关联四个独立域只读展示，固定显示 Shadow 状态、时间窗口、阈值和风险分；通用事件规则继续显示规则名称、规则编码、场景说明、事件类型、启用状态、时间窗口、触发阈值、风险分、风险等级、处置动作、更新时间和版本号。

#### 规则操作

- 新建规则：编码唯一且只允许安全字符；名称、事件类型、时间窗口、阈值、风险分、等级和动作必填并校验范围。
- 编辑规则：使用版本号或 revision 做并发控制；版本冲突时显示“规则已被其他管理员修改”，并提供重新加载，不覆盖对方修改。
- 启用/停用规则：必须有明确状态和成功反馈，停用规则不能参与判定。
- 测试规则：输入事件类型和次数，展示是否命中、风险分、等级、动作以及命中的条件。
- 通用规则不提供删除能力；退役的 V1 注册身份、V1 IP 多账号和正常 API 观察规则在 V2 首次启用的一次性迁移中移除，系统审计保留删除数量。

规则动作的界面文本使用：仅记录、人工复核、封禁账号、拒绝注册、自动封禁。`observe`、`review`、`ban`、`reject_candidate`、`auto_ban` 只作为 API 值。

规则页应为通用事件规则提供新建表单和常用模板，但模板只是预填表单，保存前仍需管理员确认。模板覆盖登录失败爆发、API 错误爆发、内容风险、配额滥用和上游错误；V2 身份规则不通过通用模板创建或编辑。

#### 后端契约

现有 `PUT /api/v1/admin/rules/{code}` 和规则测试接口继续兼容；需要补充 `POST /api/v1/admin/rules`。创建接口必须：

- 校验编码重复、字段范围、事件类型和动作值。
- 返回明确的 4xx 错误，不把用户输入错误包装成 500。
- 写入 `create_rule` 审计记录。
- 使用数据库唯一约束防止并发重复创建。
- 为内存仓储和 SQL 仓储分别提供测试。

Sub2API 管理端代理必须只允许已认证管理员访问规则创建、修改、测试接口。

### 3.3 操作记录

页面名称为“操作记录”。显示管理员账号、操作时间、操作类型、目标用户/规则、操作前后状态、操作原因、执行结果、失败原因和请求标识。

操作类型和结果全部中文展示，例如：封禁用户、解封用户、新建规则、修改规则、启用规则、停用规则、规则测试；结果为成功、部分成功、失败、待处理。

支持按管理员账号、目标用户 ID/账号、操作类型、执行结果、时间范围筛选；支持按时间、结果和目标排序；支持分页。失败记录必须显示后端返回的实际错误原因，不能只显示“操作失败”。

批量操作每个目标用户生成独立审计记录，并额外保留一个批次标识，便于从一次批量操作追踪所有目标。

## 4. 中文显示规则

建议新增集中映射文件 `frontend/src/utils/userRiskControlLabels.ts`，不要在三个 Vue 页面内各自维护映射。至少提供：

- `formatRiskType`
- `formatRiskLevel`
- `formatRiskAction`
- `formatAccountStatus`
- `formatAuditResult`
- `formatRiskReason`
- 对应的筛选项数组

映射缺失时显示“未知类型（原始值）”，不能显示空白，也不能静默丢失信息。中文标签要与 `frontend/src/i18n/locales/zh/admin/userRiskControl.ts` 保持一致；英文和日文 locale 仍需保留可用回退文本。

## 5. 权限与安全边界

- 三个页面只对已认证管理员开放，后端代理必须再次校验管理员身份，不能只依赖前端路由。
- 浏览器不得直接访问风险服务；统一通过 Sub2API 同源管理代理。
- 风险服务不得直接修改 Sub2API 用户主表；账号状态变化由 Sub2API 的状态接口执行。
- 自动封禁必须默认关闭或处于 review/shadow 模式，确认真实事件、账号身份、风险原因和审计链路后再启用。
- 所有封禁、解封和规则变更都必须有管理员、目标、原因、时间和结果。
- 不在日志、前端或提交中输出 token、内部密钥、完整敏感凭据。

## 6. 实现顺序

按以下顺序交付，避免先做视觉骨架：

1. 先补充中文映射、数据类型和 API 契约测试。
2. 实现用户页筛选、身份/原因显示、排序和批量处置。
3. 实现规则创建后端、代理、API 适配器和前端表单。
4. 实现审计字段补全、中文显示、筛选排序和批量审计。
5. 使用真实或回填的测试数据做浏览器冒烟测试，确认三个页面均能完成闭环。
6. 再做样式整理、空状态、加载状态、错误状态、响应式和无障碍检查。

不接受只完成页面骨架、静态按钮或只改文字就宣布完成。

## 7. 验收标准

### 自动化检查

- 风控服务：`go test ./...`
- 前端风控相关测试：`pnpm --dir frontend exec vitest run src/views/admin/__tests__ src/api/admin/__tests__ src/utils/__tests__`
- 前端类型检查：`pnpm --dir frontend typecheck`
- 前端构建：`pnpm --dir frontend build`
- 代码规范：`pnpm --dir frontend lint:check`
- 仓库检查：`git diff --check`

### 功能验收

- 页面主表不再直接显示英文枚举。
- 能看到用户账号、风险类型中文名、风险原因、事件时间和证据。
- 能筛选、排序、全选当前页、批量封禁和批量解封，并显示部分失败。
- 能新建规则、编辑规则、启停规则和测试规则。
- 规则版本冲突不会覆盖他人修改。
- 操作记录能查到管理员、目标、原因、结果和失败原因。
- 未登录或非管理员调用接口返回拒绝，不能只依靠隐藏菜单。
- 无数据时显示清晰空状态；有真实事件时不再显示“暂无数据”作为唯一信息。

## 8. 发布边界

本规格完成不等于已发布生产。代码开发、提交推送、本地测试、风险服务镜像发布、Sub2API 主应用发布和生产验收分别报告。

生产发布必须遵循 `AGENTS.md` 和 `deploy/RELEASE-RUNBOOK.md`：先备份 PostgreSQL、Compose/config、Nginx，使用批准的 `origin/custom-release` commit 和 Actions/GHCR 双 digest，通过管理员触发的持久发布任务发布，并检查主应用、风控服务、数据库、Redis、内部健康接口和公网 HTTPS。未获得明确发布授权时，只做本地开发和测试。
