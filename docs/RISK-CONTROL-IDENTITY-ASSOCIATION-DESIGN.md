# 风控身份关联与证据中心完整设计方案

状态：设计已确认并完成实现；生产按 Stage 0-3 分阶段启用，不迁移或反推 V1 真实身份
适用项目：Sub2API Custom Release / Extensions-Self
关联规格：`docs/RISK-CONTROL-ADMIN-SPEC.md`
确认日期：2026-08-12

## 1. 已确认的产品决策

本方案以以下决策为固定输入，实施时不得自行降级或改变：

1. 所有已认证管理员均可在风控详情中直接看到完整真实 IP，不增加单独的查看权限或点击解密步骤。
2. 真实 IP、身份关联和聚合数据暂不设置自动过期时间，永久保留，直到管理员以后明确修改保留策略。
3. 第一阶段采用免费、低侵入的设备识别方案，不接入付费设备指纹服务，不采集 Canvas、WebGL、字体列表等侵入式浏览器信号。
4. 所有新增身份关联规则上线后先运行 14 天 Shadow，仅记录和展示，不拒绝注册、不封禁账号。
5. IP 风控和设备风控作为两个独立风控域采集、统计、评分、启停和展示；综合关联作为第三个派生域，只组合查看共同证据，不改变两边的原始统计。

即使完整 IP 对全部管理员可见，系统仍须记录管理员对身份详情页的访问审计，但审计记录不得包含 IP 原文。

## 2. 目标与非目标

### 2.1 目标

管理员应当能够回答以下问题：

- 一次注册、登录或 API 风险事件来自哪个真实客户端 IP，IP 对应哪个国家、地区、城市、ASN 和运营商。
- 某个浏览器实例首次和最后一次出现于何时，使用过哪些 IP，关联过多少个注册成功账号。
- 某个真实 IP 在指定时间窗内注册成功了多少个不同账号，相关账号邮箱和状态是什么。
- 两个账号为什么被关联，是只共享 IP、只共享浏览器实例，还是同时共享 IP 和浏览器实例。
- 当前风险摘要由哪些独立规则组成，每条规则使用了哪些证据，哪些只是观察数据而非风险。
- IP 解析或设备采集异常时，系统是否自动停止使用不可信数据参与风险判定。

### 2.2 非目标

第一阶段不实现：

- 识别一台物理电脑或手机的硬件序列号。
- 跨浏览器、清 Cookie 后仍保证识别为同一物理设备。
- 通过 Canvas、WebGL、字体、音频等信号建立侵入式浏览器指纹。
- 机器学习黑盒评分、自动账号封禁或自动拒绝注册。
- 从历史 SHA-256 哈希反推出旧真实 IP、旧设备 ID 或未注册邮箱原文。
- 把 IP 地理位置精确到门牌或把城市定位作为封禁依据。

## 3. 关键术语

为避免把不同概念混成“设备”，界面和 API 统一使用下列术语：

| 名称 | 含义 | 可信度 | 能否代表物理设备 |
|---|---|---:|---|
| 真实客户端 IP | 经可信代理链解析后的客户端公网 IPv4/IPv6 | 高，受代理链质量影响 | 否 |
| 浏览器实例 | 服务端下发的第一方随机 `HttpOnly` Cookie，当前有效期 180 天 | 中高 | 否 |
| 浏览器特征 | 浏览器、主版本、操作系统、设备类别、语言等粗粒度组合 | 中低 | 否 |
| API 客户端标识 | API Key 内部 ID 派生的关联键 | 高，代表凭据来源 | 否 |
| IP 网段 | IPv4 `/24` 或 IPv6 `/64` 的弱关联维度 | 低 | 否 |
| 关联账号 | 与某 IP、浏览器实例或 API 客户端产生过指定事件的用户账号 | 取决于证据组合 | 不适用 |

管理端不得把“浏览器实例”简称成物理“设备”。为了适应用户习惯，栏目可命名为“设备/浏览器实例”，并在值旁明确显示类型。

### 3.1 三层风控模型

系统明确分成三个相互独立但可组合查询的风控域：

| 风控域 | 主键维度 | 独立统计 | 独立规则 | 独立健康状态 | 典型用途 |
|---|---|---|---|---|---|
| IP 风控域 | `network_identity_id` | IP、网段、地区、ASN、账号数和事件数 | 是 | 是 | 发现同一网络短时批量注册 |
| 设备风控域 | `device_identity_id` | 浏览器实例、API 客户端、特征、账号数和 IP 数 | 是 | 是 | 发现同一浏览器实例注册多个账号 |
| 综合关联域 | IP、设备与时间窗的交集 | 只保存或查询交集证据 | 是 | 依赖两侧健康状态 | 判断同 IP 且同浏览器实例的强关联 |

必须保持以下不变量：

- IP 计数查询不能使用设备条件，设备计数查询不能使用 IP 条件。
- IP 规则命中或停用不能改变设备规则的计数和状态，反之亦然。
- 综合规则必须同时引用一条有效 IP 证据和一条有效设备证据，并且事件时间窗有交集。
- 综合关联只是证据增强，不把同一批事件再计入 IP 或设备事件总数。
- IP 数据质量异常时，只暂停 IP 和综合规则；设备规则继续运行。
- 浏览器实例采集异常时，只暂停设备和综合规则；IP 规则继续运行。
- 管理端既能分别查看 IP、设备详情，也能在综合视图中查看交集、关联账号和证据强度。

### 3.2 证据强度矩阵

| IP 证据 | 设备证据 | 结论 | 默认强度 | 默认处置 |
|---|---|---|---:|---|
| 同 IP | 不同浏览器实例 | 可能是家庭、公司、学校、代理或运营商 NAT | 弱 | 仅观察 |
| 不同 IP | 同浏览器实例 | 同一浏览器更换网络或使用 VPN/移动网络 | 中高 | 观察或人工复核 |
| 同 IP | 同浏览器实例 | 同一浏览器和网络环境重复出现 | 高 | 人工复核候选 |
| 同 IP | 同浏览器实例且多个邮箱成功注册 | 强多账号关联 | 高 | Shadow 期仅观察 |
| 同 IP 网段 | 无相同浏览器实例 | IPv6 隐私地址或共享网段弱关联 | 很弱 | 不进入风险摘要 |
| 相同浏览器特征 | 无相同浏览器实例 | 大众浏览器/系统组合碰撞概率高 | 很弱 | 只展示，不评分 |

“强关联”表示证据强，不等于已经证明恶意；账号封禁仍需要业务行为或人工复核支持。

## 4. 总体架构与代码边界

### 4.1 结论

本功能约 80% 可以放在扩展体系中，但不能完全只修改 `extensions-self` 容器：

| 责任 | 所属位置 | 预计占比 | 原因 |
|---|---|---:|---|
| 身份数据表、加密、HMAC、地区解析、关联聚合、规则、重算 | `extensions-self/risk-control/` | 55%–65% | 风控数据和规则本来就归扩展数据库 |
| 扩展中心管理界面、类型、详情表格和筛选 | `frontend/src/features/extensions/` 及现有风控页面 | 20%–25% | 产品入口仍在扩展中心 |
| 真实 IP、请求头、浏览器 Cookie 和 API Key 来源采集 | 主后端现有风险 Hook | 10%–15% | 这些值只存在于主站请求上下文 |
| 关联用户邮箱和账号状态补全 | 主后端 `CustomUserHandler` | 5%–10% | 主用户库是账号身份的唯一权威来源 |

不修改 Sub2API 主用户表，不让风控服务直接写主数据库，也不在官方高频路由和网关处理器中新增风控逻辑。

### 4.2 数据流

```text
浏览器 / API 客户端
        |
        v
Cloudflare / Nginx / 可信代理链
        |
        v
Sub2API 主后端
  - 解析真实 IP
  - 读取浏览器实例 Cookie
  - 读取 UA / Client Hints
  - 识别 API Key 内部 ID
  - 非阻塞投递身份事件
        |
        | 内网 HMAC 签名请求
        v
extensions-self 风控模块
  - 校验签名和字段
  - HMAC 生成稳定关联键
  - 加密保存真实 IP
  - 本地/可信头地区解析
  - 分别更新账号-IP和账号-设备关联
  - 派生 IP + 设备综合证据
  - 分域计算规则信号和用户摘要
        |
        v
risk-control-postgres
        |
        v
主后端 CustomUserHandler
  - 代理扩展查询
  - 从主用户库批量补全邮箱和状态
        |
        v
扩展中心管理页面
```

### 4.3 主站稳定性边界

必须遵守：

- 身份采集不得新增第三方网络请求。
- 真实 IP 只能通过新的专用内部身份契约传递；现有通用 `RiskEventReport` 继续保持不包含原始 IP、原始设备 ID、凭据和请求体。
- 专用身份契约继续使用现有时间戳、Nonce 和 HMAC 签名，并设置严格字段白名单、字符串长度和请求体上限。
- IP 地区解析不得在注册、登录或 API 请求线程中执行。
- 正常事件通过有界、非阻塞队列异步投递；队列满时丢弃风控观察并记录指标，不阻塞业务请求。
- 14 天 Shadow 期间，注册预检不等待扩展服务给出拒绝结论；扩展不可用时主站继续注册、登录和 API 服务。
- 主站的 `RISK_CONTROL_DECISION_FAIL_MODE` 保持 `open`。
- 风控数据库迁移失败只能使扩展身份功能不可用，不能使 Sub2API 主服务退出或停止处理流量。
- 管理页面查询慢或失败不能影响用户侧接口。
- 不在核心 `router.go`、网关路由组装、官方 `UserHandler`、Wire 图和主用户表中扩展实现。

## 5. 真实 IP 采集、显示与地区解析

### 5.1 真实 IP 来源

统一复用已经修复的可信客户端 IP 解析函数，不再建立第二套解析逻辑。每次采集同时记录：

- `client_ip`：标准化后的 IPv4 或 IPv6。
- `ip_source`：`cf_connecting_ip`、`trusted_xff`、`trusted_real_ip` 或 `remote_addr`。
- `proxy_chain_valid`：是否通过可信代理链校验。
- `data_quality_flags`：例如 `private_ip`、`loopback`、`docker_gateway`、`invalid_header`、`suspected_collapsed_proxy`。

以下地址不得参与账号关联规则：

- 回环、链路本地、RFC1918 私网地址。
- Docker/Compose 网桥地址。
- 无法解析的主机名或非 IP 字符串。
- 已被数据质量检测判定为代理汇聚地址的值。

这些值仍可记录为数据质量事件，但不能计入“同 IP 多账号”。

### 5.2 存储方式

同一个真实 IP 同时生成三种数据：

1. `ip_lookup_key = HMAC-SHA256(identity_hmac_key, normalized_ip)`，用于唯一索引和关联查询。
2. `ip_ciphertext = AES-256-GCM(identity_encryption_key, normalized_ip)`，用于管理员页面解密显示。
3. `prefix_lookup_key`：IPv4 `/24` 或 IPv6 `/64` 的 HMAC，仅用于弱关联和数据分析。

不得继续用无密钥 SHA-256 作为新身份关联键。旧 `ip_hash` 只在一次性 V1 清理完成前作为 `legacy_v1` 兼容字段存在，新旧数据禁止直接合并计数。

密钥要求：

- `RISK_IDENTITY_HMAC_KEY` 和 `RISK_IDENTITY_ENCRYPTION_KEY` 分离。
- 密钥存放在知识库和 Git 仓库之外的生产凭据配置中。
- 每条加密记录保存 `encryption_key_id`，支持未来轮换。
- 数据库备份与密钥备份分别保存；两者缺一都不能恢复完整 IP。
- 应用、数据库和反向代理日志不得打印 IP 解密值或请求体。

### 5.3 IP 地区与网络信息

每个 IP 维度保存：

- 国家代码和国家名。
- 省/州、城市。
- 时区。
- ASN 和自治系统组织/运营商。
- 网络类型：住宅、移动、数据中心、代理、VPN、Tor、未知。
- 数据来源和数据库版本。
- 查询时间、地区置信说明。

解析优先级：

1. 经验证确实来自 Cloudflare 的位置请求头。
2. 本地 MaxMind GeoLite2 City + ASN 数据库。
3. 无结果时显示“地区未知”，不得调用在线 IP 查询接口阻塞请求。

Cloudflare 位置头只有在来源链可信时才能使用。直连源站或无法验证来源时，忽略客户端自行提供的 `CF-*` 位置头。

生产环境的 Cloudflare 地区阶段使用边缘 Transform Rule 覆盖专用
`X-Risk-CF-*` 头，并同时校验 `CF-Connecting-IP`、可信客户端 IP 与
`X-Forwarded-For` 最后一跳的 Cloudflare 官方 CIDR。源站即使仍可直连，直连请求
也不能伪造为可信地区。该阶段通过独立 `stage4-geo` 配置发布开启，不改变永久
Shadow、不启用拒绝或自动封禁。Cloudflare 未提供字段时保留“地区不可用”，不在
业务请求中调用在线 IP API。

城市定位只能作为辅助证据。风险规则最多使用国家变化、ASN/网络类型和粗粒度区域，不使用经纬度或城市距离直接封禁。

### 5.4 管理端显示

所有管理员默认可见完整 IP，例如：

```text
240e:3b1:xxxx::1234
中国 · 广东 · 深圳 · AS4134 中国电信
来源：可信代理链  首次：2026-08-12 10:20  最近：2026-08-12 14:51
```

支持按完整 IP 精确搜索。第一阶段不支持网段模糊搜索和批量导出，避免大范围提取个人网络数据。

## 6. 浏览器实例和设备特征

### 6.1 浏览器实例

继续使用现有服务端生成的第一方 `risk_device` Cookie，但在数据和界面中将其定义为“浏览器实例”：

- 由加密安全随机数生成。
- Cookie 格式升级为带版本和服务端签名的值，例如 `v2.<random_id>.<mac>`；服务端验证失败时不得接受为设备证据。
- `HttpOnly`、`Secure`、`SameSite=Lax`。
- Cookie 原始值不写数据库，只生成 HMAC 关联键。
- 默认有效期保持 180 天；每次有效访问可按产品策略续期。
- 管理端显示稳定短编号，例如 `B-7F3A91`，短编号不可反推出 Cookie。

Cookie 被清理、使用无痕模式或更换浏览器后，会生成新的浏览器实例。这是预期行为，界面必须明确说明，不能将多个实例自动合并为同一物理设备。

客户端可以主动删除、复制或构造 Cookie，因此浏览器实例不能只依赖“随机值看起来足够长”。必须：

- 使用独立 `RISK_DEVICE_COOKIE_SIGNING_KEY` 做 HMAC 签名，并保存签名版本/密钥 ID。
- 拒绝格式错误、签名错误、超长和未知版本的值，生成新实例并记录数据质量事件。
- 统计同一账号或 IP 的浏览器实例异常重置率，但“重置 Cookie”本身不作为恶意结论。
- 不允许前端 JavaScript 读取或指定浏览器实例 ID。
- 密钥轮换时接受有限时间内的旧签名并重新签发，不能把全部正常浏览器瞬间变成新设备。
- 签名只能防止任意伪造，不能防止复制或回放一个合法 Cookie；发现同一实例在矛盾浏览器特征或大量并发地区出现时应降低可信度并提示复核，不能据此宣称是同一物理设备。

### 6.2 浏览器特征

不新增阻塞式前端 SDK。由主后端从现有请求头采集并规范化：

- User-Agent。
- `Sec-CH-UA`、`Sec-CH-UA-Platform`、`Sec-CH-UA-Mobile`，存在时使用。
- 浏览器家族和主版本。
- 操作系统家族和主版本。
- 设备类别：桌面端、手机、平板、机器人、未知。
- `Accept-Language` 的首选语言。

原始 User-Agent 不永久写入通用事件表；规范化后保存可读字段，并对规范化组合生成 `profile_key`。`profile_key` 只能作为辅助证据，绝不能独立判定两个账号来自同一设备，因为大量正常用户可能具有相同浏览器和系统组合。

### 6.3 API 客户端

API 请求没有浏览器 Cookie 时，必须把来源单独记录为“API 客户端”，不再伪装成浏览器设备：

- 使用 API Key 内部数据库 ID 生成 HMAC 关联键。
- 不保存或传输完整 API Key。
- 管理端显示 `API 密钥 K-29A4`，可关联到主站已有的密钥名称时只显示名称和内部 ID。
- API Key 轮换会生成新的客户端标识，不推断为同一物理机器。

### 6.4 可信度

每条设备关联展示可信度：

| 证据 | 可信度 | 用途 |
|---|---:|---|
| 同一浏览器实例 HMAC | 中高 | 多账号注册关联 |
| 同一 API Key 内部 ID | 高 | API 使用来源关联 |
| 相同浏览器特征组合 | 低 | 辅助说明，不单独命中风险 |
| 同一 IP + 同一浏览器实例 | 高 | 强关联证据，仍需人工复核 |

## 7. 账号关联数据模型

### 7.1 新增表

建议以加法式迁移新增以下表，不破坏现有 `risk_events` 和 `risk_subjects`：

#### `risk_network_identities`

每个真实 IP 一行：

- `id`
- `lookup_key`，唯一 HMAC
- `ip_ciphertext`
- `encryption_key_id`
- `ip_version`
- `prefix_lookup_key`
- `ip_source`
- `proxy_chain_valid`
- `country_code`、`region`、`city`、`timezone`
- `asn`、`asn_org`、`network_type`
- `geo_source`、`geo_version`、`geo_resolved_at`
- `data_quality_flags`
- `first_seen_at`、`last_seen_at`

#### `risk_device_identities`

每个浏览器实例或 API 客户端一行：

- `id`
- `identity_kind`：`browser_instance` 或 `api_key`
- `lookup_key`，唯一 HMAC
- `display_code`
- `profile_key`
- `browser_family`、`browser_major`
- `os_family`、`os_major`
- `device_class`、`language`
- `confidence`
- `first_seen_at`、`last_seen_at`

#### `risk_user_ip_links`

按账号和 IP 聚合：

- `user_id`、`network_identity_id`
- `first_seen_at`、`last_seen_at`
- 注册尝试、注册成功、登录成功、登录失败、API 请求和异常请求计数
- `first_registration_at`、`last_registration_at`
- 主键：`(user_id, network_identity_id)`

#### `risk_user_device_links`

按账号和浏览器实例/API 客户端聚合，字段与 IP 关联表相似，主键为 `(user_id, device_identity_id)`。

#### `risk_registration_evidence`

只保存注册相关证据：

- `event_id`
- `user_id`，注册未完成时为 0
- `email_lookup_key`
- `network_identity_id`
- `device_identity_id`
- `outcome`：`attempt`、`success`、`failure`
- `failure_class`，不保存密码、验证码或原始请求体
- `occurred_at`

成功注册账号的邮箱从主用户库实时补全。匿名失败尝试只显示邮箱短指纹，例如 `E-83A1`；不为显示失败邮箱而永久保存其原文。

#### `risk_identity_activity_daily`

按天聚合正常 API 活动，避免永久保留策略导致每个成功 API 请求无限增长：

- 日期、用户、IP、API 客户端、事件分类、请求数、错误数、首次和最后时间。
- 正常 API 请求不再作为低风险原因写入用户摘要。
- 内容风险、配额异常、登录失败等真正的风险事件继续保留明细。
- 为防止投递重试重复累加，允许保留一个最长 2 天的事件键去重账本；其中不得含 IP、设备、邮箱、用户正文或可逆身份值，不属于永久身份与证据数据。超过账本覆盖窗口才送达的普通 API 成功事件直接丢弃，不得在键过期后重新累计。

#### `risk_signals`

每个用户、规则和证据对象保存一条独立信号：

- `user_id`、`rule_code`、`evidence_key`
- `signal_domain`：`ip`、`device`、`composite`、`account`、`api` 或 `data_quality`
- `score`、`risk_level`、`action`
- `reason_template` 和结构化证据
- `source_evidence_ids`：综合信号引用的 IP 和设备证据 ID，不复制原始事件
- `correlation_id` 和 `evidence_version`，用于解释、重算和审计
- `first_hit_at`、`last_hit_at`、`expires_at`
- `status`：`observing`、`active`、`reviewed`、`dismissed`、`expired`

这样可以同时显示多个命中规则，不再由单个 `risk_subjects.reason` 覆盖所有历史原因。

### 7.2 现有表兼容

- `risk_events` 增加可空的 `network_identity_id`、`device_identity_id`、`identity_version` 和 `data_quality_valid`。
- V2 首次启用时执行一次经数据库迁移版本保护的 `legacy_v1` 清理；删除旧 `risk_events`、对应事件键和 `risk_subjects` 投影，不尝试反推或迁移旧 `ip_hash`、`device_hash`、`email_hash`。
- 清理前必须由发布流程备份独立风控数据库；管理员操作审计、V2 身份事实、关联、信号和主用户数据不在清理范围内。
- `risk_subjects` 继续作为列表页快速摘要，但由可重复执行的重算任务从 `risk_signals` 生成。
- V2 Schema 迁移保持加法式；经管理员明确批准的一次性 V1 清理是唯一删除性迁移。普通应用回滚不删除或恢复身份数据。

### 7.3 永久保留

根据已确认决策，V2 身份数据不设置 TTL，也不运行自动删除任务。为控制长期增长：

- 正常 API 请求只保留日聚合，不永久保存每次成功请求明细。
- `risk_registration_evidence` 和高价值风险事件按月分区。
- 查询索引围绕 `lookup_key`、`user_id`、`occurred_at` 和成功注册结果建立。
- 备份必须包含身份表、分区、加密密钥 ID 和地区数据库版本。
- 保留管理员发起的单用户删除/匿名化能力，供未来合规或用户删除请求使用；该能力不等于自动 TTL。

## 8. 关联统计口径

所有关联数量必须同时给出时间窗和事件结果，不允许只显示没有口径的“账号数”。

### 8.1 IP 关联

对每个 IP 展示：

- 历史关联账号总数。
- 最近 10 分钟、1 小时、24 小时和 7 天的注册成功账号数。
- 注册尝试邮箱指纹数。
- 浏览器实例数和 API 客户端数。
- 当前正常、禁用、待审核账号数。
- 首次和最近事件时间。

风险规则只使用“不同成功账号数”或“不同邮箱指纹数”，不使用原始事件总数。一次注册过程中的多次提交不得被当作多个账号。

### 8.2 浏览器实例关联

对每个浏览器实例展示：

- 历史关联成功账号数。
- 最近 24 小时和 7 天的新注册账号数。
- 使用过的真实 IP 数、国家数、ASN 数。
- 浏览器和系统特征是否发生变化。
- Cookie 首次和最后出现时间。

### 8.3 关联账号列表

每个关联账号返回：

- 用户 ID、完整邮箱、用户名、账号状态和创建时间。
- 关联类型：同 IP、同浏览器实例、两者同时、同 API 客户端。
- 首次关联、最近关联、时间重叠范围。
- 注册成功证据数、登录证据数、API 活动聚合数。
- 证据强度：弱、中、强。

成功账号身份由主后端从主用户库批量补全。扩展服务只返回用户 ID 和关联证据，不直接读取主用户表。

### 8.4 综合关联

综合关联按“同一成功账号注册事件或明确重叠时间窗中的 IP + 浏览器实例”计算，不以用户历史上分别出现过某 IP 和某设备就判定两者同时出现。

综合视图展示：

- IP、地区、ASN 和网络类型。
- 浏览器实例短编号、浏览器和操作系统。
- 两者共同出现的首次、最近时间和共同事件数。
- 共同关联的成功账号数和账号明细。
- 是否同一注册事件、同一会话或只是时间窗重叠。
- 引用的 IP 证据 ID、设备证据 ID 和规则版本。

综合证据必须从不可变事件事实或关联表 Join 得出，不能通过拼接两个摘要计数推断。

### 8.5 采集覆盖矩阵

身份采集必须覆盖完整认证生命周期，不能只覆盖最终注册接口：

| 场景 | IP | 浏览器实例 | 浏览器特征 | API 客户端 | 明细/聚合 |
|---|---:|---:|---:|---:|---|
| 发送邮箱验证码 | 必须 | 必须 | 必须 | 不适用 | 反滥用明细 |
| 邮箱注册尝试/失败 | 必须 | 必须 | 必须 | 不适用 | 注册证据明细 |
| 邮箱注册成功 | 必须 | 必须 | 必须 | 不适用 | 注册证据明细 |
| OAuth 开始/回调/完成注册 | 必须 | 必须 | 必须 | 不适用 | 注册阶段证据 |
| 登录尝试/失败/成功 | 必须 | 必须 | 必须 | 不适用 | 风险明细 |
| 管理员登录 | 必须 | 必须 | 必须 | 不适用 | 独立审计，不参与普通用户规则 |
| API 正常请求 | 必须 | 有则记录 | 有则记录 | 必须 | 日聚合 |
| API 错误/内容/配额事件 | 必须 | 有则记录 | 有则记录 | 必须 | 风险明细 |

所有场景复用同一身份解析结果和同一请求级 `identity_context`，不得在不同 Handler 中各自重新解释代理头、Cookie 或 User-Agent。

## 9. 风险规则设计

### 9.1 原则

- 邮箱重复提交、同 IP、同浏览器实例必须是三种独立口径。
- 每条规则必须声明 `signal_domain`，同一规则不得使用“IP 或设备”这种无法解释的合并条件。
- 综合规则使用明确的 `AND` 条件；需要 `OR` 的业务场景拆成两条独立规则。
- 观察数据不得产生风险等级或覆盖用户风险摘要。
- 同 IP 单独命中永远不能自动封禁。
- 数据质量无效的 IP 不参与任何用户规则。
- 规则计数默认使用不同账号、不同邮箱或不同对象，而不是事件总数。
- 第一版摘要分数取当前有效信号的最高分，不叠加相似规则分数，避免重复证据导致分数膨胀。
- 综合信号与其引用的 IP、设备信号属于同一证据家族；摘要取该家族最高分，不把三者相加。

### 9.2 初始规则建议

以下阈值是 14 天 Shadow 的起始值，最终值必须根据生产分布调整：

| 风控域 | 规则 | 时间窗与阈值 | 初始分 | Shadow 动作 | 说明 |
|---|---|---|---:|---|---|
| 账号 | 同邮箱注册重试观察 | 10 分钟内同邮箱尝试 5 次 | 0 | 仅记录 | 不进入风险摘要 |
| 设备 | 同浏览器实例多邮箱尝试 | 10 分钟内不同邮箱 5 个 | 30 | 观察 | 可能是批量注册 |
| 设备 | 同浏览器实例多账号成功 | 24 小时内成功账号 3 个 | 50 | 观察 | 中强关联 |
| 设备 | 同浏览器实例长期多账号 | 7 天内成功账号 5 个 | 70 | 观察 | 待人工复核 |
| IP | 同 IP 多账号成功 | 1 小时内成功账号 5 个 | 30 | 观察 | 共享网络可能误报 |
| IP | 同 IP 大量账号成功 | 24 小时内成功账号 10 个 | 55 | 观察 | 排除代理汇聚和无效 IP |
| 综合 | 同 IP + 同浏览器实例 | 24 小时内成功账号 2 个 | 60 | 观察 | 强关联但不自动封禁 |
| IP | 同 IP 验证码发送爆发 | 10 分钟内 10 次 | 30 | 观察 | 与设备规则独立 |
| 设备 | 同浏览器实例验证码发送爆发 | 10 分钟内 10 次 | 40 | 观察 | 与 IP 规则独立 |
| IP | 新国家登录 | 30 天未见国家登录成功 | 20 | 观察 | 仅提示 |
| IP | 不可能位置变化 | 2 小时内跨国家且 ASN 明显变化 | 45 | 观察 | VPN 场景需复核 |
| 设备 | API 客户端多账号 | 同 API 客户端关联不同账号 2 个 | 60 | 观察 | 一般应高度关注 |

14 天结束时输出每条规则的命中账号数、人工确认数、误报数、共享网络占比和建议阈值。未经明确审批，不把动作从 `observe` 改为 `review`、`reject_candidate` 或 `auto_ban`。

### 9.3 删除误导规则

`API 请求观察（24 小时内 N 次事件）`不再作为用户风险规则：

- 正常 API 请求进入日聚合和使用基线。
- 用户风险摘要不显示“低风险”。
- API 异常规则只统计用户自身错误、配额、内容风险等事件。
- IP 或浏览器关联仅作为证据维度，不把其他用户的请求数累加到当前用户。

## 10. 用户风险摘要重算

V2 上线后执行一次全量重算，之后支持增量和可重复全量重算。

摘要生成顺序：

1. 确认在线库已完成一次性 `legacy_v1` 清理；只在清理前 Dry Run 中排除已知代理解析错误的数据。
2. 排除 `data_quality_valid=false` 的 IP 证据。
3. 按独立规则重新生成 `risk_signals`。
4. 分数为有效风险信号最高分；分数 0 的观察项不产生风险等级。
5. 摘要原因列出最高优先级信号，详情展示全部信号。
6. 没有有效风险信号的用户显示“暂无风险”，但仍可查看身份和活动统计。
7. 重算记录版本、规则修订号、开始结束时间、处理行数和差异统计。

重算必须先支持 Dry Run，输出以下对账结果后才能写入：

- 旧/新风险用户数。
- 各等级增减。
- 各规则命中数。
- 被移除的旧 API 观察摘要数。
- 被判定为代理数据污染的事件数。
- 随机抽样用户的关联账号和事件证据。

写入式重算必须由服务端同时校验：持久化的 14 天 Shadow 截止时间已经到达、同一管理员在 30 分钟内完成 Dry Run，且 Dry Run 后身份事件和规则均未变化；审批校验、证据与规则水位检查、候选生成和写入必须位于同一可串行化事务，并在事务期间锁定身份事件和规则表，避免检查后数据变化；任一条件不满足时返回冲突并记录失败审计。

## 11. 管理端产品设计

### 11.1 用户列表

保持扩展中心现有“用户风控”入口，新增紧凑列：

- 最近真实 IP 及国家/地区。
- 浏览器实例数、API 客户端数。
- 关联成功账号数。
- 当前有效规则数量。
- 数据质量状态。

列表不直接加载所有完整关联详情，避免 N+1 查询。完整 IP 和关联邮箱只在详情请求中返回。

### 11.2 用户详情

详情抽屉改为四个标签页：

1. **风险摘要**：有效规则、分数、结构化原因、处置历史。
2. **IP 与地区**：完整 IP、地区、ASN、网络类型、时间、账号数和事件数。
3. **设备/浏览器实例**：实例短编号、浏览器、系统、类型、可信度、IP 数和账号数。
4. **关联账号**：完整邮箱、用户 ID、状态、关联依据、时间窗和证据强度。

每个 IP 和浏览器实例行可以展开查看关联账号，但不使用复杂关系图作为第一阶段主交互。表格更适合管理员扫描、比较和复核。

风险摘要增加三个并列分区：`IP 风控`、`设备风控`、`综合关联`。每个分区独立显示健康状态、有效规则数、最高分和原因；页面顶部的总风险只取有效证据家族的最高等级，不把三栏分数相加。

### 11.3 数据质量提示

页面顶部增加身份数据健康状态：

- 真实 IP 解析正常。
- IP 风控域：正常、降级或暂停。
- 设备风控域：正常、降级或暂停。
- 综合关联域：正常、因 IP 异常暂停或因设备异常暂停。
- 发现私网/Docker 网关 IP，已从规则排除。
- 某一 IP 占据异常高比例用户，IP 关联规则已暂停。
- 地区数据库过期或不可用。
- 身份加密密钥不可用。
- 事件队列发生丢弃。

数据质量异常时，页面必须明确说明“关联统计可能不完整”，不能静默继续评分。

### 11.4 查询接口

扩展服务新增：

- `GET /api/v1/admin/users/{id}/identity-summary`
- `GET /api/v1/admin/users/{id}/ip-identities`
- `POST /api/v1/admin/users/{id}/ip-identities/search`（精确 IP 放入 JSON 请求体，不进入 URL）
- `GET /api/v1/admin/users/{id}/device-identities`
- `GET /api/v1/admin/users/{id}/associated-users`
- `GET /api/v1/admin/work-overview`
- `GET /api/v1/admin/identity-health`
- `POST /api/v1/admin/risk-rebuilds/dry-run`
- `POST /api/v1/admin/risk-rebuilds`
- `GET /api/v1/admin/risk-rebuilds/{id}`

`identity-health` 同时承担管理能力发现：即使 `RISK_IDENTITY_ADMIN_ENABLED=false` 也返回 `200`，并明确给出 `admin_enabled=false` 及三个域的 `disabled` 状态。只有扩展不可达、签名失败、数据库或健康计算故障才返回错误；前端必须把“未启用”和“服务不可用”分开展示。其他身份详情、关联和重算端点在管理开关关闭时继续拒绝访问。

主后端 `CustomUserHandler` 增加组合查询：

- 调用扩展服务获取关联用户 ID 和证据。
- 使用主站管理服务批量读取邮箱、用户名、状态和创建时间。
- 合并后返回同源管理 API。
- 不把主数据库凭据或读取权限交给扩展服务。

所有接口必须分页、限制最大页大小、只允许管理员、设置 `no-store`，并避免在错误信息中返回密文或密钥标识细节。

工作概览由扩展服务一次聚合返回待复核、当前管理员案件、观察中、当前有效风险和数据异常数量。内部 `GET /api/v1/admin/risk-index` 统一投影通用风险主体与当前有效身份信号，按风险分、最近命中和用户 ID 提供稳定服务端分页；默认列表只批量补全响应页账号，账号或状态跨主库筛选时按最多 100 个 ID 的批次筛选风险候选后再分页，并在主库查询层排除风险账号后分页普通账号。关联账号继续由主后端按最多 100 个 ID 的批次补全；前端不得为了排序、筛选或分页拉取全量账号。精确 IP 查询的旧 GET 参数仅为兼容旧客户端保留，当前管理端必须使用 POST JSON 契约，通用审计中间件整体省略该请求体，专用查看审计只记录目标账号和分区。

本次为覆盖密码登录、2FA、verified-email OAuth、pending OAuth binding/exchange、OIDC fast-path、LinuxDo、WeChat、DingTalk 和 passkey 登录成功，显式评审并固定以下 Stable 基线差异预算：`auth_handler.go` 21 个 added lines / 12 个自定义 marker，`auth_email_oauth.go` 7/2，`auth_oauth_pending_flow.go` 8/2，`auth_oidc_oauth.go` 8/2，`auth_linuxdo_oauth.go` 2/1，`auth_wechat_oauth.go` 1/1，`auth_dingtalk_oauth.go` 1/1，`passkey_handler.go` 9/3。新增行仅调用 `reportIdentityLoginSuccess` 或完成相邻控制流，不解析 IP、Cookie、地区，不访问扩展数据库，也不改变认证或令牌签发结果；对应生命周期合同由 `deploy/tests/risk-identity-contract.test.mjs` 和后端全量测试覆盖。后续不得仅为通过 CI 再放宽这些预算。

### 12.3 前端修改

- 扩展风控 API 类型和适配器。
- 用户详情的四个标签页和分页表格。
- IP/地区、浏览器实例、关联账号和数据质量组件。
- 风险规则说明和 Shadow 状态。
- 中文、英文、日文标签回退。

路由继续通过 `frontend/src/features/extensions/install.ts` 动态安装，不修改中央路由表。

## 13. 功能开关与灰度

建议新增独立开关：

- `RISK_IDENTITY_V2_ENABLED`：采集和写入 V2 身份数据。
- `RISK_IDENTITY_ADMIN_ENABLED`：管理端查询与展示。
- `RISK_IDENTITY_RULES_ENABLED`：身份关联规则计算。
- `RISK_IDENTITY_IP_RULES_ENABLED`：只控制 IP 风控规则。
- `RISK_IDENTITY_DEVICE_RULES_ENABLED`：只控制设备风控规则。
- `RISK_IDENTITY_COMPOSITE_RULES_ENABLED`：只控制综合关联规则；任一基础域不健康时自动失效。
- `RISK_IDENTITY_SHADOW_UNTIL`：固定 Shadow 截止时间。
- `RISK_IDENTITY_GEO_SOURCE`：已激活的可信地区来源；生产当前使用 `cloudflare_verified`，扩展契约同时保留 `maxmind_local`。

发布顺序：

1. 上线加法式数据库表和密钥配置，所有功能开关关闭。
2. 开启 V2 采集，确认主站延迟、错误率和队列丢弃无异常。
3. 开启管理端展示，核对真实 IP、地区、浏览器实例和关联账号。
4. 开启身份规则 Shadow，运行完整 14 天。
5. 执行风险摘要 Dry Run 并人工抽样。
6. 确认后写入 V2 摘要；是否进入人工复核模式另行审批。

本设计不包含自动封禁启用步骤。

## 14. 测试与验收

### 14.1 自动化测试

后端和扩展必须覆盖：

- IPv4、IPv6、IPv4 映射 IPv6、端口、无效地址规范化。
- Cloudflare、X-Forwarded-For、X-Real-IP 和 RemoteAddr 的可信链优先级。
- 客户端伪造转发头被拒绝。
- 私网、回环、Docker 网关不会参与规则。
- HMAC 稳定、不同密钥隔离、AES-GCM 加解密和篡改失败。
- 浏览器 Cookie 首次生成、复用、Secure 属性和清理后新实例。
- API Key 身份与浏览器实例分离。
- 同邮箱重试、同 IP 多账号和同浏览器实例多账号计数完全独立。
- 关闭 IP 规则不影响设备计数和信号，关闭设备规则不影响 IP 计数和信号。
- 综合规则只在 IP 和设备证据共同出现且时间窗重叠时命中。
- 同一证据家族的 IP、设备和综合分数不会重复相加。
- 正常 API 请求只计入当前用户聚合，不扩散到同 IP 用户。
- 关联账号分页、邮箱批量补全和删除账号降级显示。
- Shadow 规则不会拒绝注册或封禁用户。
- 扩展不可用、队列满、地区库不可用时主业务继续成功。
- V1 清理前的 Dry Run 与清理后的纯 V2 重算均可重复且结果一致。

### 14.2 性能门槛

- 用户侧请求不执行同步地区查询。
- 异步身份入队本地基准 p95 小于 1 ms。
- 队列满时立即丢弃观察事件，不等待扩展服务。
- 扩展身份写入使用 Upsert 和批量聚合，不为正常 API 请求无限插入明细。
- 在一百万风险事件规模下，单用户身份详情第一页 p95 小于 500 ms。
- 管理端首次只加载摘要，展开标签页后再分页加载明细。

### 14.3 生产验收

- 关闭或停止 `extensions-self` 后，注册、登录和 API 请求仍正常。
- 新注册用户能看到正确完整 IP、地区、浏览器实例和成功账号关联。
- 同邮箱连续提交只增加重试观察，不产生多账号结论。
- 同 IP 不同浏览器注册能正确显示共享 IP，但不显示共享浏览器实例。
- 同浏览器实例更换 IP 后仍能关联实例，并分别显示两个 IP。
- IP、设备和综合三栏能分别查看，综合栏能准确显示两者共同出现的事件。
- 人为暂停 IP 域后，设备域继续产生 Shadow 信号，综合域自动暂停。
- 同一 IP 下多个正常用户不会继承彼此 API 请求数。
- `API 请求观察`不再出现在用户风险摘要。
- 所有新增规则在 14 天内均为 Shadow，没有自动处置。
- 管理员查看详情有审计记录，审计中不含完整 IP。
- 完成一次性 V1 清理后管理端不再展示旧身份/API 规则及其历史事件；备份中的 V1 数据仍不得伪造真实 IP 或与 V2 混算。

## 15. 监控与数据质量保护

至少暴露以下指标：

- 身份事件入队、成功、失败、丢弃和延迟。
- IP 来源分布和无效 IP 数。
- 私网、Docker 网关和代理汇聚事件数。
- 单一 IP 关联用户占比。
- IP、设备和综合三个域各自的启用、降级、暂停状态。
- V2 事件缺少浏览器实例、UA 或 API 客户端的比例。
- 加密/HMAC 错误。
- 地区解析成功率、数据库版本和过期状态。
- 关联查询耗时和结果数量。
- 每条 Shadow 规则命中用户数与人工判定结果。

自动保护条件：

- 若单一 IP 在短时间覆盖异常比例的活跃用户，标记 `suspected_collapsed_proxy` 并暂停所有 IP 关联规则。
- 若可信 IP 解析成功率跌破阈值，仅保留事件，不计算 IP 风险。
- 若身份加密密钥不可用，拒绝写入真实 IP 字段并报警，不回退到明文存储。
- 若地区库过期，继续显示最后一次地区结果并标注过期，不阻塞业务。
- 若浏览器实例 Cookie 缺失率或异常重置率超过阈值，暂停设备和综合规则，但继续运行 IP 规则。

## 16. 迁移、发布与回滚

### 16.1 迁移

- 发布前备份主 PostgreSQL、`risk-control-postgres`、Compose、Nginx 和密钥配置。
- 先执行只新增 V2 对象的 Schema，再在发布备份成功后执行一次性 V1 清理迁移。
- V2 首次启用时按已确认的清理决策批量删除旧 `risk_events`、事件键和旧摘要；不修改或回填旧记录。
- 清理动作写入系统审计并记录删除数量；应用回滚不自动恢复已删除数据，需要时只能从发布前风控数据库备份人工恢复。
- 第一次摘要重算必须先 Dry Run 并保存差异报告。

### 16.2 发布

代码完成、提交、推送、Actions/GHCR、生产备份、管理员触发发布和生产验收分别报告。生产只能使用批准的 `origin/custom-release` 提交和成对镜像 Digest，通过现有管理员更新流程发布。

### 16.3 回滚

- 功能异常时先关闭 V2 采集、管理端或规则开关。
- 主站保持 fail-open，不需要回滚主用户库。
- 代码回滚不删除新增表、列或已采集身份数据。
- 只有确认 Schema 或数据损坏并获得明确授权后，才从风险数据库备份恢复。
- 密钥错误时不得生成新密钥覆盖旧密钥；必须恢复对应 `key_id` 的原密钥。

## 17. 安全和隐私边界

尽管产品决定永久保留并向所有管理员显示完整 IP，仍必须执行最小化保护：

- 只有管理员同源接口能返回解密 IP。
- 不提供匿名公共接口、普通用户接口或批量导出接口。
- 不在前端缓存、LocalStorage、URL 查询参数或错误上报中保存 IP。
- API 响应设置 `Cache-Control: no-store`。
- 管理员详情访问写审计，但审计只记录管理员 ID、目标用户 ID、时间和结果。
- 不保存密码、验证码、Token、完整 API Key、请求体或请求头集合。
- 匿名失败注册邮箱只保存关联键，不保存可恢复原文。
- 未来改变永久保留政策时，必须同时覆盖在线表、分区、备份和密钥处置。

## 18. 完成定义

只有同时满足以下条件，才能声明该功能完成：

- Schema、加密、关联聚合、规则和重算代码完成并通过测试。
- 主后端只存在经审查的最小身份采集和组合查询改动。
- 扩展中心能展示完整 IP、地区、浏览器实例和关联邮箱。
- 数据质量异常会暂停不可信规则。
- 正常 API 请求不会污染其他用户摘要。
- 扩展服务不可用时主站功能不受影响。
- 生产运行完 14 天 Shadow 并形成阈值复核报告。
- V2 摘要 Dry Run与人工抽样一致后才正式写入。
- 发布、备份、健康检查和回滚证据完整记录。

## 20. 补充建议与优先级

### 20.1 P0：实施前必须完成

1. **三域硬隔离**：IP、设备、综合关联使用独立计数函数、规则编码、信号域、开关和健康状态，禁止用通用 `associated_events` 查询承载新规则。
2. **签名浏览器 Cookie**：当前随机 Cookie 需要升级为服务端签名格式，防止客户端任意构造设备 ID；复制、回放和频繁重置仍需通过可信度和数据质量规则处理。
3. **请求级身份上下文**：真实 IP 只解析一次，浏览器实例和客户端类型只识别一次，再传给注册、登录和 API 风控 Hook。
4. **综合证据同现约束**：必须证明 IP 和浏览器实例在同一事件、同一会话或明确重叠窗口共同出现，不能把两个历史摘要简单拼接。
5. **重复计分防护**：同一证据家族只取最高信号，综合规则不能与来源 IP/设备规则叠加总分。
6. **数据质量熔断**：出现 Docker 网关、代理汇聚、IP 解析成功率下降或 Cookie 异常重置时，按域暂停规则。

### 20.2 P1：首个生产版本推荐完成

1. **共享网络标签**：管理员可以把某 IP 标记为家庭、公司、学校、公共代理、可信出口或未知；标签带原因、管理员和时间，仅用于降低 IP 证据权重，不删除事实。
2. **人工判定反馈**：每条信号支持标记“确认风险、正常共享、证据不足、数据错误”，用于 14 天 Shadow 报告和阈值调整。
3. **IPv6 专门口径**：完整 IPv6 精确关联与 `/64` 网段弱关联分开。IPv6 隐私地址轮换不能直接视为多个独立家庭或设备。
4. **CGNAT/移动网络降权**：移动运营商、云出口、学校和大型 ASN 的同 IP 多账号阈值应高于住宅固定 IP；只作为权重，不作为绝对判断。
5. **邮箱身份状态**：关联账号区分成功账号、匿名尝试邮箱指纹、已删除账号和无法解析身份，避免把尝试数显示成注册账号数。
6. **事件幂等**：所有身份事件使用稳定事件键，注册预检、成功回报和重试投递不能重复累计。

### 20.3 P2：Shadow 数据稳定后再考虑

1. 账号关系图，仅作为表格之外的辅助视图，不替代证据表。
2. 可信设备标记和管理员手动解除关联，但解除只能影响处置建议，不能修改原始事实。
3. 可配置 ASN、国家、网络类型白名单/观察名单，并保留版本和审计。
4. 基于用户自身历史基线的新地区、新 ASN、新浏览器实例提醒。
5. 数据容量看板，包括永久保留下的明细、分区、索引和备份增长预测。

### 20.4 不推荐

- 不推荐把 IP、浏览器实例、User-Agent 或 API Key 任意一个叫作“设备指纹”。
- 不推荐用相同 User-Agent 或浏览器特征独立关联账号。
- 不推荐把同 IP 账号数、同设备账号数和事件次数直接相加为风险分。
- 不推荐在用户请求路径同步调用 MaxMind Web Service 或其他在线 IP API。
- 不推荐为了历史完整性尝试破解旧 SHA-256 IP 哈希。
- 不推荐在 Shadow 结束前启用拒绝注册或自动封禁。
